# Единый деплой на Yandex Cloud и безопасный Preview

## Целевая схема

Разработка всего приложения в Lovable → проверка Preview и тестов → GitHub → одна команда на Mac:

```bash
cd ~/Desktop/pravdarula && ./deploy-yandex.sh
```

Команда сохраняется. Единый скрипт определяет необходимые обновления; отдельные обычные команды frontend-only/backend-only не нужны. Yandex Cloud остаётся единственным production-бэкендом.

## Что уже есть и чего не хватает

- Production: статический интерфейс в Object Storage, API Gateway, Node.js Cloud Function, YDB, Postbox и Lockbox.
- Скрипт сейчас подтягивает `main`, собирает интерфейс, загружает статику, создаёт версию Cloud Function и обновляет Gateway при каждом запуске. Нет учёта применённых миграций, проверенного релиза и автоматического выбора изменённых частей.
- `create-auth-schema.mjs` создаёт три таблицы авторизации, но не является системой миграций всей базы. Существующие таблицы и данные нужно принять как исходное состояние, а не пересоздавать.
- Preview использует локальные демонстрационные данные и не вызывает настоящий API. На production-доменах демо выключено, но его модули пока присутствуют в общих импортируемых исходниках.
- Унаследованное `demoForm` используется и в обычной анкете; это отдельно устранить, чтобы пустые реальные поля не заполнялись демонстрационными значениями перед сохранением.

## 1. Постоянная изоляция Preview

- В сборке для Yandex явно выключить демо через отдельный флаг сборки. Любое отсутствие флага разрешения трактовать как запрет.
- Для Lovable Preview включать демо только при сочетании разрешённой сборки и проверенного адреса Preview этого проекта. `NODE_ENV`, параметры URL и подставленные заголовки не являются разрешением.
- Разделить реальные и демонстрационные реализации кабинетных операций. Из production-сборки исключить демо-пользователя, исходные демо-покупки и хранилище Preview; проверить готовые артефакты, а не только исходники.
- На Яндексе не добавлять ни demo-токены, ни доверие к demo-ID, ни обход проверки сессии. Существующие публичные endpoints сохраняют свои ограничения.
- Настоящая ветка сохраняет последовательность входа: email-код → HttpOnly-сессия → знакомство → кабинет. Демо-анкета и покупки остаются только в отдельном хранилище Preview.
- Добавить тесты отрицательных адресов и production-сборки, тест обычного входа с имитированным API и сценарий Preview, падающий при любом обращении к настоящему API.

## 2. Один универсальный deploy-yandex.sh

- Сохранить текущую команду и ресурсы; не создавать инфраструктуру заново.
- Проверять чистую рабочую копию, доступ к GitHub и Яндексу, версии инструментов, зависимости и наличие необходимых настроек без вывода секретов.
- После безопасной синхронизации зафиксировать точный commit релиза. Сравнивать его с последним успешно опубликованным commit и контрольными суммами релиза.
- Рассчитывать граф зависимостей: изменения интерфейса обновляют статику; изменения API и импортируемой им бизнес-логики обновляют Cloud Function; спецификация маршрутов обновляет Gateway; новые миграции применяются отдельно внутри того же скрипта. Общие каталоги, зависимости и конфигурация сборки учитываются во всех затронутых частях.
- До любых записей показывать перечень обновлений и запрашивать подтверждение. Неизвестные изменения и отсутствующий исходный релиз требуют явного решения, а не молчаливого пропуска.
- Все необходимые сборки и локальные тесты выполнить до публикации. Не считать весь релиз атомарным: Object Storage, Gateway, функции и YDB обновляются раздельно.
- Загружать новые неизменяемые ресурсы раньше HTML. Проверять совместимость старого интерфейса с новым API и наоборот, прежде чем переключать версии. Отдельно согласовать отказ от маршрутизации через `$latest` в пользу управляемого стабильного тега/версии — сейчас `$latest` не позволяет безопасно подготовить функцию без её немедленного включения.
- Сохранять manifest релиза: commit, версии функций, контрольную сумму Gateway, список миграций и файлы интерфейса. При ошибке не отмечать релиз успешным; предлагать восстановление предыдущих кода и статики без автоматического удаления данных.

## 3. Миграции и новые функции

- Ввести упорядоченные миграции YDB с журналом применений, контрольными суммами, блокировкой параллельных запусков и безопасным повторным запуском.
- Сначала сверить текущую схему production в режиме чтения и принять baseline. Не запускать существующий тестовый скрипт создания таблиц как миграцию всей базы.
- Учитывать ограничения YDB: не обещать транзакционный откат всех DDL; фиксировать незавершённые изменения и останавливать последующие этапы.
- По умолчанию разрешать совместимые добавления; удаление/переименование колонок, преобразование данных и другие рискованные действия требуют отдельного подтверждения и плана восстановления.
- Новые API-функции добавляются в существующий Yandex-обработчик и Gateway. Если функции требуют новых облачных ресурсов или прав, перечислять их для отдельного согласования, не создавать автоматически.

## 4. Проверка backend внутри Lovable

Демо-авторизация — это удобный вход для разработки, не замена тестирования настоящего сервера. Preview с mock-объектами не проверяет YDB, доставку писем, webhook и оплату end-to-end.

- Выделить бизнес-логику в проверяемые модули и запускать тесты Yandex API с имитацией базы, почты и платежей внутри Lovable.
- Учитывать разные среды: Preview-сервер Lovable и Node.js-функция Яндекса не взаимозаменяемы. Облачный обработчик не переносить в Lovable Cloud.
- Для реальных интеграционных проверок понадобится отдельно согласованный изолированный тестовый контур Yandex Cloud, без доступа демо к production. В этот этап его создание не входит.

## 5. Критерии готовности

- Production-сборка не содержит активируемой демо-реализации; на pravdarula.ru сохраняются настоящие вход, сессия и выход.
- Preview открывает демонстрационный кабинет, не создаёт реальных пользователей, заказов или платежей и не обращается к production API.
- Та же команда показывает проверяемый план релиза и публикует только необходимые части всего проекта.
- Миграции не повторяются бесконтрольно; ошибки оставляют понятное состояние и инструкции восстановления.
- Документация заменяет прежнее предложение frontend-only единым процессом.

## Границы согласования

После одобрения — изменения исходников, тестов, конфигурации сборки и deploy-скрипта, но без запуска деплоя. Любые реальные миграции, переключение версии/тега функции, изменение Gateway, ресурсов или production выполняются только после отдельного согласования. Автоматическую проверку неизменённого production можно выполнять только без записей и реальных платежей.
