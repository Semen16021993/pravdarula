# Развертывание «Право Руля» в Yandex Cloud

Проект собирается как статическая SPA. Файлы интерфейса хранятся в Object Storage и раздаются через API Gateway. Серверная часть работает в Cloud Functions и использует YDB и Cloud Postbox.

## Архитектура

- Object Storage (`pravdarula.ru`) — статические файлы интерфейса.
- API Gateway (`pravdarula-production`) — единая HTTPS-точка входа для SPA и API.
- Cloud Functions (`pravdarula-api`) — авторизация, личные кабинеты, заказы, оплата и webhook.
- Managed YDB — пользователи, одноразовые коды, сессии, анкеты, заказы и покупки.
- Cloud Postbox (`auth.pravdarula.ru`) — одноразовые коды входа.
- Lockbox (`pravdarula-runtime-secrets`) — `AUTH_SECRET`.
- Lockbox (`pravdarula-yandex-pay`) — тестовый ключ `YANDEX_PAY_SANDBOX_API_KEY`; доступ выдан runtime service account.

Lovable используется как редактор исходного кода. Для работы сайта не требуется Lovable Cloud или Supabase.

## Локальная сборка

```bash
npm run build:yandex
./yandex-api/build.sh
```

Статические файлы собираются в `.output/public`, архив Cloud Function — в `yandex-api/pravdarula-api.zip`.

## Секреты и платежи

`AUTH_SECRET` хранится в Lockbox и передается Cloud Function как переменная окружения.

Сейчас оставлен тестовый контур: `YANDEX_PAY_ENV=sandbox`, `YANDEX_PAY_MERCHANT_ID` задан, а `YANDEX_PAY_SANDBOX_API_KEY` хранится в Lockbox `pravdarula-yandex-pay`. В Sandbox ключ Merchant API совпадает с Merchant ID. Боевой ключ не нужен и не используется. Для будущего перехода в live потребуется отдельно выпустить боевой ключ и переключить `YANDEX_PAY_ENV=live`. Ключи нельзя помещать в браузерный код или build arguments.

## Деплой

1. Один раз скопировать `.deploy-yandex.env.example` в локальный `.deploy-yandex.env` и заполнить параметры Yandex Cloud. Файл с реальными настройками игнорируется Git.
2. Для следующего обновления выполнить:

```bash
cd ~/Desktop/pravdarula && ./deploy-yandex.sh
```

Скрипт проверяет чистоту рабочей копии и ветку `main`, получает изменения GitHub только fast-forward, фиксирует точный commit, показывает план обновлений и требует интерактивное подтверждение `DEPLOY` до любых записей в облако. Нужны Node.js 22+, npm, Bun (для корневого bun.lock), yc CLI, curl и shasum.

Состояние релизов хранится вне репозитория в `~/.cache/pravdarula-releases/<target>/` (либо XDG_CACHE_HOME): `current.json` — последний успешный релиз, `pending.json` — начатый релиз, снимки ресурсов и резервная копия статики. Не удалять эти файлы для обхода проверки. Первый запуск без исходного manifest считается полным релизом и требует отдельного согласования. Не запускать параллельно с другого Mac: глобальная блокировка всего релиза пока не настроена.

Изменения интерфейса выбирают статику; изменения Yandex API — Cloud Function; изменения Gateway — его спецификацию; изменения транзитивных локальных импортов API (например каталога/цен) выбирают также сервер. Изменения зависимостей затрагивают обе части. Неизвестные пути консервативно выбирают все части и показываются для проверки. Изменение параметров развёртывания определяется по контрольной сумме и тоже требует рассмотрения.

Перед публикацией устанавливаются зависимости из lockfile, запускаются тесты и необходимые сборки. Готовая статика проверяется на маркеры демо-пользователя и демо-хранилища. Новые ресурсы загружаются до HTML, старые хешированные ресурсы не удаляются. После публикации проверяются health, страница и отсутствие сессии у нового запроса `/api/auth/me`. Реальную оплату и отправку писем скрипт не выполняет.

Gateway пока использует `$latest`: создание новой версии функции может сразу включить API. Скрипт отдельно предупреждает и требует подтверждения совместимости старого и нового интерфейса/API. Переход на стабильный тег требует отдельного согласования и сейчас не выполнен. Общий релиз не атомарен; при сбое manifest не отмечается успешным. Восстановление кода/статики выполняется после проверки снимков; база автоматически не откатывается.

### Миграции YDB

Версионированные миграции размещаются в `yandex-api/migrations/NNN_name.json`: `id`, `safety` (`additive` или `destructive`), `idempotent` и массив `statements`. Пока миграций нет, runner не подключается к базе и не создаёт таблиц. `baseline.json` — предполагаемые существующие колонки, а не исполняемая миграция.

При появлении миграций runner сначала проверяет существующие колонки запросами без чтения данных. Перед первым применением нужно отдельно сверить реальные типы, ключи и индексы и согласовать `APPROVE_YDB_BASELINE=yes`: только тогда создаются служебные journal/lock таблицы. Эта живая проверка пока не выполнена.

Журнал содержит checksum и состояния running/applied/failed. Применённые миграции не исполняются повторно; изменённые или удалённые применённые файлы останавливают релиз. Незавершённая миграция требует ручной проверки и явного `RESUME_MIGRATION=<id>` только для подтверждённо идемпотентной миграции. Рискованные изменения требуют `APPROVE_DESTRUCTIVE_MIGRATIONS=yes` после отдельного согласования. При падении процесса блокировка базы не истекает автоматически: её снимают вручную только после проверки предыдущего запуска. DDL не считается атомарным с записью журнала.

### Разработка и Preview

Lovable Preview требует одновременно разрешённого адреса нашего проекта и флага сборки `VITE_PREVIEW_DEMO="true"`. В Yandex-сборке флаг принудительно `"false"`; ленивые импорты демо-пользователя и покупок исключаются. В обычной анкете новые пустые поля остаются пустыми. Уже сохранённые значения не удаляются.

Mock-кабинет не вызывает production API, не создаёт реальных пользователей/заказов/платежей. Preview не проверяет настоящие YDB, Postbox и webhook: бизнес-правила и миграции тестируются на имитациях; для полноценных облачных проверок нужен отдельно согласованный изолированный контур Яндекса. Инфраструктура такого контура в этой задаче не создаётся.

**Статус:** исходники и локальные проверки подготовлены. Деплой не запускался; команды yc и миграционный адаптер не проверялись на настоящем Yandex Cloud. Перед первым production-релизом обязательны отдельное согласование baseline, сверка действующей конфигурации функции/секретов и проверка команд yc на вашем Mac. Тест компиляции главной страницы подтвердил исключение модуля `preview-cabinet`; полная сборка Yandex и проверка её статики выполняются скриптом до публикации, здесь не запускались. Тесты: 13 frontend и 15 Node; проверка Preview в браузере — ноль запросов к реальному API.

## Текущее состояние домена

- `https://pravdarula.ru` подключен к API Gateway через ANAME и действующий сертификат.
- Основной домен проверен напрямую, в обход VPN: HTML, JS, CSS, шрифты и API отвечают успешно; YDB подключена.
- Вход по email и личный кабинет имеют серверные маршруты; проверка Origin для `https://pravdarula.ru` настроена.
- `www.pravdarula.ru` сейчас отвечает редиректом 302 на `https://pravdarula.ru/`, но сам редирект пока обслуживается прежним провайдером. Чтобы обслуживать и `www` непосредственно через API Gateway, потребуется увеличить квоту Yandex Cloud с одного домена до двух.
- Платежи настроены на Sandbox; перед сквозным тестом нужно проверить, что тестовый Callback URL в кабинете Яндекс Пэй указывает на `https://pravdarula.ru` (Яндекс добавляет `/v1/webhook`). Боевой контур намеренно не включен.
