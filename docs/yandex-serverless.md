# Развертывание «Право Руля» в Yandex Cloud

Проект собирается как статическая SPA. Файлы интерфейса хранятся в Object Storage и раздаются через API Gateway. Серверная часть работает в Cloud Functions и использует YDB и Cloud Postbox.

## Архитектура

- Object Storage (`pravdarula.ru`) — статические файлы интерфейса.
- API Gateway (`pravdarula-production`) — единая HTTPS-точка входа для SPA и API.
- Cloud Functions (`pravdarula-api`) — авторизация, личные кабинеты, заказы, оплата и webhook.
- Managed YDB — пользователи, одноразовые коды, сессии, анкеты, заказы и покупки.
- Cloud Postbox (`auth.pravdarula.ru`) — одноразовые коды входа.
- Lockbox (`pravdarula-runtime-secrets`) — `AUTH_SECRET`.
- Lockbox (`pravdarula-yandex-pay`) — тестовый ключ `YANDEX_PAY_SANDBOX_API_KEY`; доступ выдан runtime service account.

Lovable используется как редактор исходного кода. Production не зависит от Lovable Cloud.

## Локальная сборка

```bash
npm run build:yandex
./yandex-api/build.sh
```

Статические файлы собираются в `.output/public`, архив Cloud Function — в `yandex-api/pravdarula-api.zip`.

## Секреты и платежи

`AUTH_SECRET` хранится в Lockbox и передается Cloud Function как переменная окружения.

Сейчас оставлен тестовый контур: `YANDEX_PAY_ENV=sandbox`, `YANDEX_PAY_MERCHANT_ID` задан, а `YANDEX_PAY_SANDBOX_API_KEY` хранится в Lockbox `pravdarula-yandex-pay`. В Sandbox ключ Merchant API совпадает с Merchant ID. Боевой ключ не нужен и не используется. Для будущего перехода в live потребуется отдельно выпустить боевой ключ и переключить `YANDEX_PAY_ENV=live`. Ключи нельзя помещать в браузерный код или build arguments.

## Деплой

1. Один раз скопировать `.deploy-yandex.env.example` в локальный `.deploy-yandex.env` и заполнить параметры Yandex Cloud. Файл с реальными настройками игнорируется Git.
2. Для следующего обновления выполнить:

```bash
cd ~/Desktop/pravdarula && ./deploy-yandex.sh
```

Скрипт остаётся единственной точкой полного релиза. Он проверяет чистую ветку `main`, получает GitHub fast-forward, устанавливает зафиксированные зависимости и запускает локальные тесты. Внутренний `scripts/release-runner.mjs` выполняет планирование, проверки, публикацию и восстановление. Отдельных штатных команд frontend/backend нет.

Нужны Bash, Git, Node.js 22+, npm, Bun, yc CLI, **YDB CLI (`ydb`)**, curl и zip. Локальный `.deploy-yandex.env` содержит IDs ресурсов, адрес базы, путь `YDB_TOKEN_FILE` к файлу IAM access token с правами 0600, пути к отчётам. Секреты авторизации и оплаты не копируются: используются существующие Lockbox bindings, включая точные версии.

### План и защита конфигурации

- Backend-зависимости берутся из metadata того же esbuild, который собирает API; учитываются текущий и предыдущий графы. Вычисляемые импорты блокируются до анализа.
- Изменения интерфейса выбирают статику. Общие модули, используемые сервером, выбирают и API. Любое изменение `yandex-api/` (кроме миграций) требует также проверки Gateway. Все литеральные методы/пути действующего диспетчера сопоставляются с Gateway, включая существующий POST-алиас `/api/cabinet/form`.
- Неизвестные пути блокируют релиз. Отдельный локальный `RELEASE_PATH_REVIEW_FILE` может подтвердить только уже поддерживаемые/неисполняемые файлы точного commit и hash. Новые неподдерживаемые серверные маршруты и `.functions` не становятся рабочим API по такому подтверждению: сначала нужна реализация в Yandex handler/Gateway и тесты.
- Текущая версия определяется по реальному тегу Gateway, не по времени создания или `$latest`. Проверяются Function/Gateway IDs, folder, runtime service account, bucket и отклонения от последнего manifest.
- Проверяется весь поддерживаемый снимок конфигурации версии: runtime, entrypoint, память, timeout, environment, secrets, connectivity, logging, mounts, concurrency, metadata и прочее. Неизвестное поле останавливает релиз. Настройки версии-кандидата клонируются через `--source-version-id`; результат читается обратно и сравнивается с полной исходной конфигурацией до включения.
- AUTH_SECRET и Sandbox Pay secret проверяются по ID/key/**непустой version_id**. Не закреплённая/неожиданная binding блокирует запуск. `YANDEX_PAY_ENV=sandbox` сохраняется; иное значение запрещено. Дополнительные environment variables сохраняются, а заданные в локальном конфиге значения должны совпасть с действующими.

### Проверки до включения нового API

Перед созданием кандидата текущая версия получает тег `release-<old-version-id>` и Gateway переключается на **тот же прежний код** по этому тегу. Только после чтения Gateway обратно создаётся новый кандидат: изменение `$latest` больше не активирует API сайта. Кандидат получает собственный тег `release-<new-version-id>`, проходит сравнение конфигурации и безопасные проверки health и signed-out auth. Новые файлы интерфейса загружаются до переключения Gateway на кандидата; обе переходные комбинации обязаны быть совместимы.

Первое закрепление текущего API — изменение Gateway/тега, которое будет выполнено только при отдельно согласованном настоящем запуске. Сейчас в облаке ничего не переключено. Внешние потребители прямого `$latest`, если они существуют вне проверенного Gateway, требуют отдельного анализа: скрипт не обнаруживает их автоматически.

Изменения API, Gateway или pending миграции требуют `RELEASE_COMPATIBILITY_FILE`: exact commit, previousVersion, frontendHash, backendHash, gatewayHash и четыре записи `checks`: `oldFrontendNewBackend`, `newFrontendOldBackend`, `signedInSession`, `sandboxPayment`. Каждая запись содержит `passed: true`, абсолютный путь `report` к реально проведённой проверке и `sha256` этого отчёта. Скрипт сверяет идентичность артефактов/отчётов, **но не проводит эти четыре живые проверки сам и не может доказать правдивость отчёта оператора**. Их нужно выполнить в согласованном изолированном контуре, не на mock-авторизации Preview.

При отсутствии отчётов попытка завершается до записей и сохраняет `compatibility-required.json`. После проверок повторяется та же команда. ZIP API имеет фиксированные времена и исключённые дополнительные metadata для повторяемого hash. Повторяемость полной Vite-сборки требуется проверить на Mac: изменение build-артефактов потребует новых отчётов.

### Состояние и восстановление

Состояние хранится вне репозитория: `~/.cache/pravdarula-releases/<target>/` (либо XDG_CACHE_HOME). Каждый запуск имеет уникальный `release-*/` со снимками Function/Gateway, предыдущим manifest, резервной копией статики и контрольными суммами. `pending.json` записывается **до первой записи в облако** и перед каждым опасным этапом. `current.json` заменяется только после проверки активного тега, Gateway, всех публикуемых файлов по hash, health и отсутствия signed-out сессии.

Незавершённый релиз блокирует новый. Та же команда предлагает `RECOVER`, а не новую публикацию. Восстановление проверяет snapshots/backup, наличие прежней Function, отсутствие посторонних изменений Gateway, затем закрепляет прежнюю версию, возвращает прежние файлы (ресурсы перед index.html), прежнюю спецификацию Gateway с закреплённым тегом и предыдущий manifest. Файлы проверяются по hash, API — health/auth; только после успеха удаляется pending. Новая неактивная версия Function и новые лишние hashed assets не удаляются. `$latest` не возвращается назад: production использует сохранённый закреплённый тег.

Content-Type/Cache-Control/Encoding/Language/Disposition резервных объектов читаются из S3 и восстанавливаются. Неподдерживаемая пользовательская metadata/expiry блокирует релиз до записей. ACL, object tags и расширенные параметры бакета не являются частью автоматического восстановления — их не следует менять в этом процессе.

Если уже начиналось применение миграций, автоматическое восстановление кода **останавливается**: прежний код может быть несовместим с изменившейся YDB. Нужно проверить journal и фактический DDL, согласовать восстановление базы из проверенного backup либо доказать совместимость прежнего кода с новой схемой и провести контролируемое восстановление. Скрипт не содержит автоматического rollback YDB и не имеет обходного флага для удаления pending.

Локальный lock не имеет срока истечения. После аварийного завершения нужно убедиться, что на Mac не выполняется релиз, изучить pending/snapshots и только затем удалить **пустой lock**, не pending. Затем та же команда предложит восстановление. Блокировка всего релиза между разными Mac пока не реализована: используйте один согласованный Mac/оператора.

### Миграции YDB

Read-only проверка выполняется даже при отсутствии новых миграций: `ydb scheme describe ... --format proto-json` проверяет типы/nullability, порядок primary key, определения индексов и неволатильные опции таблиц. Охват: пять source-known таблиц baseline и таблицы предыдущих миграций, а не автоматическая инвентаризация произвольных ресурсов базы. Known auth-типы сверяются с исходной схемой. Точные типы cabinets/orders, индексы и опции не угадываются: первый снимок должен быть явно изучен и принят (`SCHEMA`). Дальнейшие отличия от `schema-accepted.json` блокируют запуск.

Файлы `yandex-api/migrations/NNN_name.json` применяются по **числовому** префиксу; повтор номера запрещён. Полный pending план проверяется до любого DDL. Автоматически допускается только один идемпотентный additive statement на миграцию с полной `expectedAfter` схемой затронутых таблиц и конкретным текстом `recovery`. Destructive и многокомандный DDL блокируются до реализации отдельно отрепетированного внешнего восстановления: одного `APPROVE_DESTRUCTIVE_MIGRATIONS=yes` недостаточно.

Перед DDL требуется отдельное интерактивное `MIGRATE`, привязанное к hash файлов и наблюдаемой схеме. Изменившийся план блокируется при apply. Journal/locks создаются только при первой реально одобренной миграции; без миграций нет служебных DDL. Journal проверяется и при пустом наборе файлов, чтобы удаление ранее применённой миграции не осталось незамеченным. Applied checksum пропускается; running/failed не повторяются автоматически. После каждого statement фактическая схема сверяется с expectedAfter до записи applied. Ошибка фиксируется failed и останавливает релиз. DDL, bootstrap journal и запись статуса не атомарны: pending сохраняет необходимость ручного анализа частичного результата.

### Разработка и Preview

Lovable Preview требует одновременно разрешённого адреса нашего проекта и флага сборки `VITE_PREVIEW_DEMO="true"`. В Yandex-сборке флаг принудительно `"false"`; ленивые импорты демо-пользователя и покупок исключаются. В обычной анкете новые пустые поля остаются пустыми. Уже сохранённые значения не удаляются.

Mock-кабинет не вызывает production API, не создаёт реальных пользователей/заказов/платежей. Preview не проверяет настоящие YDB, Postbox и webhook: бизнес-правила и миграции тестируются на имитациях; для полноценных облачных проверок нужен отдельно согласованный изолированный контур Яндекса. Инфраструктура такого контура в этой задаче не создаётся.

**Статус:** локальные защитные механизмы и репетиции подготовлены; облачные команды с записью и deploy не выполнялись. Живые настройки Function/Lockbox/Gateway, IAM, реальный формат DescribeTable, bootstrap/journal, полная production-сборка на Mac и настоящий вход/Sandbox требуют отдельной проверки. Локальные имитации не являются разрешением первого production-релиза.

## Текущее состояние домена

- `https://pravdarula.ru` подключен к API Gateway через ANAME и действующий сертификат.
- Основной домен проверен напрямую, в обход VPN: HTML, JS, CSS, шрифты и API отвечают успешно; YDB подключена.
- Вход по email и личный кабинет имеют серверные маршруты; проверка Origin для `https://pravdarula.ru` настроена.
- `www.pravdarula.ru` сейчас отвечает редиректом 302 на `https://pravdarula.ru/`, но сам редирект пока обслуживается прежним провайдером. Чтобы обслуживать и `www` непосредственно через API Gateway, потребуется увеличить квоту Yandex Cloud с одного домена до двух.
- Платежи настроены на Sandbox; перед сквозным тестом нужно проверить, что тестовый Callback URL в кабинете Яндекс Пэй указывает на `https://pravdarula.ru` (Яндекс добавляет `/v1/webhook`). Боевой контур намеренно не включен.
